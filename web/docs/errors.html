Errors & rate limits

One error shape everywhere, in both implementations, asserted byte-for-byte by the shared fixtures, including the error bodies.

The error shape¶

Every error is JSON with a stable machine-readable error code, a human-readable message, and sometimes a hint:

{
  "error": "bad_request",
  "message": "Could not parse date 'bad'.",
  "hint": "Expected YYYY-MM-DD, e.g. 2026-04-12."
}

400 Bad Request¶

Malformed dates, impossible dates, unknown calendars, out-of-range values:

HTTP/1.1 400 Bad Request

{
  "error": "bad_request",
  "message": "'2026-02-31' is not a real Gregorian date."
}

Batch conversion is the exception by design: an invalid item gets a per-item error while valid items still convert; the request as a whole only fails on a malformed body (see batch conversion).

404 Not Found¶

{
  "error": "not_found",
  "message": "No route for GET /v1/nope.",
  "hint": "See / for the endpoint list."
}

429 Too Many Requests¶

HTTP/1.1 429 Too Many Requests
Retry-After: 1
Cache-Control: no-store

{
  "error": "rate_limited",
  "message": "Too many requests. Please retry after 1 seconds.",
  "retryAfter": 1
}

Client rule: wait the number of seconds in Retry-After, then retry once. Never retry in a tight loop: the token bucket refills continuously (10 tokens/second toward a 60-token burst), so a short wait always recovers capacity. /v1/health is exempt from application rate limiting and is the right probe for liveness checks.

500 Internal Error¶

{ "error": "internal", "message": "Unexpected error." }

No stack trace is ever exposed. If you can reproduce a 500, open an issue with the request path; the fixtures make regressions easy to pin down.
