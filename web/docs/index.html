EOTCDev API / Documentation

Introduction

An open, free REST API for the Ethiopian Orthodox Tewahedo Church calendar: Ethiopian↔Gregorian conversion, fasting, feasts, the full Bahire Hasab computation, and a date-level bridge between the Gitsawe, Sinksar, and Bible.

Infrastructure, not another app¶

Coptic developers have coptic.io and katameros-api to build on. The EOTC world has content mega-apps but no open backend. This project is that backend. It is deliberately boring in the right ways:

  • No auth, no API keys, no accounts. A generous anonymous rate limit prevents abuse instead.
  • No database. Every response is computed from versioned code and bundled, permitted data. Nothing about you is stored.
  • No runtime network calls. The service depends on nothing else being up.
  • MIT licensed. Vendor the zero-dependency core modules directly if you prefer no network call at all.

Your first call¶

$ curl https://eotcdev-api.natinael-96.workers.dev/v1/today
{
  "gregorian": { "date": "2026-04-12" },
  "ethiopic":  { "date": "2018-08-04", "monthName": { "amharic": "ሚያዝያ" } },
  "weekday":   { "amharic": "እሑድ", "english": "Sunday" },
  "fasting":   { "isFasting": false, "reason": "Not a fasting day." },
  "feasts":    [ { "amharic": "ትንሣኤ", "english": "Easter (Resurrection)" } ]
}

Every date-shaped response carries both calendars, in both scripts: Amharic, transliteration, and English together, so clients never make a second call or maintain their own name tables.

Base URL. Examples in these docs use the public Worker host. Self-hosting? Substitute your own host; the paths and responses are identical, held so by the conformance fixtures described below.

Two implementations, one behaviour¶

The API ships twice, on purpose:

RuntimeStackRuns on
ts/TypeScript + HonoCloudflare Workers (free tier), Node, Deno, Bun
py/Python + FastAPIAny host; automatic Swagger UI at /docs

They are not a port and a copy; they are held identical by tests:

  • spec/conformance.json: 9,154 golden calculation vectors both suites assert;
  • spec/responses.json: every route's exact HTTP response. The Python suite replays every fixture route and asserts byte-identical JSON, including error bodies and status codes.

Change one implementation without the other and a build fails. The fixtures are the reviewable HTTP contract; every example in these docs is drawn from them.

Versioning & compatibility¶

  • Existing /v1 fields will not be removed or change meaning in a minor release.
  • New optional fields and endpoints may be added to /v1 at any time; parse fields by name and tolerate additive fields.
  • A breaking response or resolver change requires /v2 with a documented migration path.
  • API behaviour, source content, generated catalogs, and (future) precedence rules are each versioned so a historical result can be reproduced.

Security & privacy¶

  • No user accounts, API keys, or personal data; no database stores client activity.
  • Rate-limit keys live only in process/edge memory.
  • Error responses never expose stack traces.
  • CORS is intentionally open; this is public infrastructure.
  • Restricted Bible and Sinksar narrative text is excluded from public runtime artifacts (see Data & sources).
